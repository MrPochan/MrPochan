# @cupquest/core

Игровое ядро «Кубкового квеста»: генератор поля шаров, бой волны, карты, экономика и состояние забега.
Детерминированная логика без Phaser, DOM, Telegram SDK и сети. Клиент и сервер используют один и тот же код.

Ссылки на разделы ТЗ: CORE-, GEN-, RNG-, CARD-, ECO-, BAL- (`ТЗ 4`), концепция (`концепция 2–3`).

## Состав

| Модуль | Содержимое |
|---|---|
| `src/prng.ts` | xoshiro128** (RNG-001..003), KDF (RNG-004) |
| `src/sha256.ts` | SHA-256 без внешних крипто-API (FIPS 180-4), hex |
| `src/board.ts` | генератор поля (GEN-001..020), сериализация 58 байт, fallback |
| `src/battle.ts` | бой волны, события с миллисекундами, журнал и его хеш (CORE-012..027) |
| `src/cards.ts` | пул, предложения, реролл-поток, модификаторы героев (CARD-001..008) |
| `src/economy.ts` | монеты, шары, улучшения, уровни, энергия, леджер (ECO-001..012) |
| `src/run.ts` | конечный автомат забега (CORE-001, 012–014, 026) |
| `src/config.ts` | типизированные значения из `src/data/*.json` |
| `src/index.ts` | публичный API |
| `scripts/build-data.ts` | сборка генерируемых данных: fallback, gates, таблица уровней |
| `scripts/build-golden.ts` | golden-векторы TV-001 (`test/golden/field_v1.json`) и гистограмма TV-005 (`test/golden/tv005_v1.json`) |
| `scripts/release-check.ts` | релизный шлюз BAL-002/CORE-009: код 1, пока есть значения `open` |
| `eslint.config.js` | правила GEN-003 для файлов генератора: `Math.random`, `Date`, `parseFloat`, дробные литералы |
| `test/support/sim.ts` | пересчет выборки BAL-005 из генератора (тесты сверяют файлы с ним) |

Запуск:

```bash

npm run typecheck -w packages/core # tsc --strict
npm run build -w packages/core     # то же, что typecheck: у ядра нет эмита, его читают сервер и клиент как исходники
npm run lint -w packages/core      # ESLint: правила GEN-003 для генератора и разбор остальных .ts
npm run release:check -w packages/core   # код 1, пока есть значения status/value = open (BAL-002)
npm run data:fallback -w packages/core   # пересборка src/data/fallback_v1.json
npm run data:gates -w packages/core      # пересборка src/data/gates.json (150 000 полей, около 4 с)
npm run data:levels -w packages/core     # сверка таблицы U(L) и суммы 29 245
npm run golden:build -w packages/core    # пересборка test/golden/field_v1.json (315 полей); меняет байты только при смене версии поля (TV-004)
npm run tv005:build -w packages/core     # пересборка test/golden/tv005_v1.json (1 000 сидов x 15 волн)
```

## Публичный API

Все примеры предполагают `import * as core from '@cupquest/core'` или именованные импорты из той же точки входа.

### Сиды и ПСЧ

```ts
const seed = fromHex('00112233445566778899aabbccddeeff');            // S, 16 байт
const sub = kdf(seed, 'field', 1, 0);                                 // KDF(S, label, i1, i2), RNG-004
```

```ts
const rng = new Xoshiro128ss(sub);
rng.next();        // беззнаковое u32 (RNG-001)
rng.bounded(7);    // 0..6, отказ по 2^32 mod n (RNG-003)
```

```ts
toHex(sha256(new TextEncoder().encode('abc')));   // 'ba7816bf…15ad'
```

### Забег

```ts
let state = startRun({ runId: 'r1', userId: 'u1', seed, team: ['knight', 'archer', 'mage'] });
const step = applyAction(state, { k: 'battle' });   // бой волны 1; step.events — события для анимации
state = step.state;                                  // phase: 'cards'
state = applyAction(state, { k: 'auto_pick' }).state;// выбор offer[0] (CARD-003)
state = applyAction(state, { k: 'drop', c: 2 }).state; // бросок из колонки 2 (CORE-013)
```

Действия: `battle` (с `commands` для воскрешения), `pick` (`card`), `reroll`, `upgrade` (`card`), `auto_pick`, `drop` (`c`, `auto`), `end` (`result`: `abandon` или `timeout`).

```ts
const entries = ledgerForRun(state, 1700000000); // проводки для submit (ECO-001)
```

## Данные

Все числа баланса записаны как `{"value": целое | null, "source": "concept:<раздел>" | "assumption" | "open"}` (BAL-002).
Загрузчик `src/config.ts` разворачивает их в обычные целые при загрузке.

| Файл | Содержимое | Источник |
|---|---|---|
| `src/data/field.json` | геометрия поля, 3 шаблона ворот, веса x0/x1/x2/x3/x5, лимит x0 | GEN-010 (геометрия и шаблоны: `assumption`, веса: `assumption`, концепция 2.3) |
| `src/data/fallback_v1.json` | 20 подсидов на волну, генерируется `scripts/build-data.ts fallback` | GEN-018 |
| `src/data/gates.json` | статистика 150 000 полей, шансы ворот, средний выход шаров | BAL-005..007, генерируется `scripts/build-data.ts gates` |
| `src/data/battle.json` | герои, враги, фазы босса, лимиты, Tmin, воскрешение, фрейм лягушки, 15 волн | ТЗ CORE-009, CORE-020, CORE-024; концепция 2.1, 2.5 |
| `src/data/cards.json` | 30 карт, эффекты по четырем тирам | CARD-001; тексты открыты, значения `open` |
| `src/data/economy.json` | монеты, таблица U(L) для L = 2..20, шары, энергия, гемы | ECO-002, ECO-004, ECO-006, ECO-011; концепция 3.1, 3.2 |
| `test/golden/field_v1.json` | векторы SHA-256, PRNG и KDF, 21 сид (G_0..G_19 и фиксированный S) x 15 волн = 315 полей с байтами и хешем | TV-001; генерирует `scripts/build-golden.ts golden` |
| `test/golden/tv005_v1.json` | гистограмма попыток, fallback, dead_end и отказов валидации на 1 000 сидах x 15 волн | TV-005; генерирует `scripts/build-golden.ts tv005` |

Тесты сверяют оба файла с генератором, а `gates.json` — с пересчетом выборки BAL-005 (`test/data.test.ts`), поэтому файлы не служат самоотчетом.

Значения `gates.json` получены симуляцией по 10 000 сидам забега (`S_k = KDF(SIM, "sim", 0, k)`).
Суммарно: x0 8,2 %, x1 16,8 %, x2 30,0 %, x3 25,0 %, x5 20,1 %; средний выход 25,20 шара за волну и 378,01 за забег
(BAL-009: 8,2 / 16,8 / 30 / 25 / 20 %; 25,2 и 377,7).

## Допущения

Значения, которых нет в спецификации или концепции, помечены `source` в данных. Ниже — решения, принятые в коде.

1. **Расположение данных.** Файлы лежат в `src/data/` (как в задаче), а не в `packages/core/data` (BAL-001). Список файлов совпадает с BAL-001.
2. **Сборка данных.** Список fallback строит `scripts/build-data.ts fallback` по правилу GEN-018. Инструмента `tools/fallback_build` в пакете нет. Файл генерируемый, правится только скриптом.
3. **BAL-002 не для структуры.** Числа, которые балансируются, обернуты в `{value, source}`. Геометрия, номера колонок, шаблоны ворот и состав (`enemy_slots`, `hero_slots`) — структурные целые, для них источник указан на уровне группы.
4. **Состав волн.** Все 15 волн в `battle.json` имеют `status: "open"` (CORE-009). Состав — заглушка, подобранная под калибровку. Релизная сборка должна падать, пока `openBalanceEntries()` не пуст.
5. **Герои.** Рыцарь 300 hp, 12 урона, период 12 тиков; Лучник 180 hp, 12 урона, период 10; Маг 160 hp, 12 урона, период 20, сплэш ±1; Друид 200 hp, 6 урона, период 10. Пара Лучник + Маг дает 36 урона в секунду (концепция 2.5, п. 3). Это сумма; разбиение по героям — допущение.
6. **Калибровка.** Цели из теста CORE-024 и приемки 4.1 выполнены: средняя обычная волна при x1 13,4–16,4 с для всех четырех команд, босс побеждается за ≤ 1 600 тиков (лимит 1 800). Волна 14 (огр и два гоблина) длится 20–25 с при x1.
7. **Единицы боя.** Атака происходит на тиках, кратных периоду: `tick % period === 0`. Фазы тика: герои по слоту, лягушки по порядку призыва, затем враги по индексу (CORE-023).
8. **Сплэш мага.** Маг бьет основную цель и живых врагов с индексом ±1 с тем же уроном (CORE-025, С16).
9. **Лягушка Друида.** Призыв каждые 400 тиков, до 2 живых, жизнь 200 тиков; урон и период в `battle.json`. Враги атакуют только героев, поэтому HP лягушки не используется, пока правило не задано.
10. **Фазы босса.** Одна фаза: при HP ≤ 50 % урон босса становится 4 вместо 2 (пороги открыты, ТЗ 9.4).
11. **Воскрешение.** Ввод `res` допустим только в шаге 1 и только один раз за забег. HP = floor(maxHP / 2). Если все герои мертвы и воскрешение зарезервировано, поражение наступает через 60 тиков после последней смерти (CORE-026).
12. **Лимит.** Мини-босс на волне 8 — 1 200 тиков (открыто). Босс — 1 800 тиков (концепция 2.5). Поражение по лимиту наступает, если к лимиту остались живые враги (CORE-021).
13. **Уровень героя.** +5 % hp и урона за каждый уровень выше 1, округление вниз, целая арифметика (ECO-004, открыто).
14. **Карты.** Тексты открыты: id `knight_01…common_06`, по одному эффекту на карту. Эффекты: `dmg` и `hp` — процент, `speed` — процент сокращения периода атаки (`floor(period·100/(100+x))`, не меньше 1). Пул сортируется по id побайтно, ASCII-id совпадают с UTF-8.
15. **Улучшение карты.** Стоимость зависит от целевого тира: 20 (тир 1), 60 (тир 2), 150 (тир 3). Улучшение не закрывает шаг 2; закрывает его только выбор карты.
16. **Шаг 2 в последней волне.** В полном забеге шага 2 нет на волне 15, в short5 — на волне 5 (победа по шагу 3). Шаг 2 в short5 есть на волнах 1–4.
17. **Short5.** Монеты волн 1–5 по ECO-002 без бонусов волн 8 и 15.
18. **Бросок.** Колонку выбирает клиент и передает в `drop`. Авто-бросок — то же действие с `auto: true`, колонка — текущая (CORE-013). Дефолтной колонки ядро не выбирает.
19. **Средний выход шаров.** Один бросок за волну попадает в колонку, выбранную равновероятно. Ожидаемый выход — среднее по колонкам (BAL-006, `avg_balls_hundredths = floor(100·сумма/(5·N))`).
20. **Запасной вариант (fallback).** Выбор по S: `bounded(20)` из потока `fallback` (GEN-017, С3). Последовательного перебора нет.
21. **Помощь (CARD-007).** `helpCard` возвращает offer[0] из потока `help`. Счетчик поражений, выдача раз в 24 часа и запись в БД — на сервере; ядро получает уже выданную карту через `initialCards` с тиром 3.
22. **Леджер.** Чистые функции без БД. Ключи по ECO-001. Баланс — сумма проводок; повтор ключа игнорируется. Отрицательный баланс шаров и монет запрещен; гемы могут уйти в минус только через возврат (ECO-010).
23. **Энергия.** Формулы ECO-011 точные. Постановка в очередь и SELECT FOR UPDATE — на сервере.
24. **Вместимость команды.** Пул 24 карты задает максимум взятий (CARD-008). Лимит слотов не вводится.
25. **Восстановление поля.** Ядро умеет восстановить поле из S (RNG-007), сервер в MVP этого не делает (С18).
26. **Тесты поля (TV-001).** `test/golden/field_v1.json` содержит 21 сид, 315 полей, 12 записей KDF, векторы SHA-256 и PRNG. Каждая запись пересчитывается и сравнивается побайтно (`golden.test.ts`). Тест KDF сверяет сообщение и подсид с описанием из RNG-004. Файл создан генератором по правилам GEN-001..020; это регрессионный эталон, независимая реализация (Python, Chromium, WebView) — TV-003, открыто.
27. **TV-002, поле с `attempt ≥ 1` (открыто).** Естественного поля с `attempt ≥ 1` нет. Поиск: около 1,55·10⁸ проверок попытки 0 на случайных подсидах (отдельно для каждой из 15 волн), ни одного `dead_end` и ни одного отказа проверки. Верхняя 95-процентная граница вероятности отказа попытки около 2·10⁻⁸, поэтому естественное поле с `attempt ≥ 1` при GEN-014 практически не возникает. Пункт не закрыт тестом, потому что тест, утверждающий отсутствие, закреплял бы невыполненное требование. Ветка попыток проверяется подменой построителя (`generateWith`, `board.test.ts`, не экспортируется из индекса), ветка fallback — тоже подменой. Для закрытия нужна поправка спецификации TV-002 или правило GEN-014, которое дает хотя бы один тупик (решение владельца).
28. **GEN-003.** ESLint 10 с `typescript-eslint` (пакет `core`, `npm install <pkg> -w packages/core`). Правила `no-restricted-globals` (`Date`, `parseFloat`), `no-restricted-properties` (`Math.random`) и `no-restricted-syntax` (дробные литералы) действуют на `src/board.ts`, `src/prng.ts`, `src/sha256.ts`, `src/cards.ts`. `test/lint.test.ts` запускает ESLint на этих файлах, проверяет, что правила срабатывают на плохих примерах, и прогоняет генератор с `Math.random` и `Date`, замененными бросающими функциями. CI в репозитории нет: проверка входит в `npm test` и в `npm run lint`.
29. **Скорость x1/x2 (CORE-011).** В API боя нет параметра скорости. Лог и исход одинаковы по построению.
30. **Релизный шлюз (BAL-002, CORE-009).** `release:check` выходит с кодом 1, пока `openBalanceEntries()` не пуст. Сейчас 160 значений открыто. Обычная сборка (`build`, `test`) не блокируется, как и тестовая сборка. Релиз клиента: `npm run release -w packages/client` вызывает шлюз и потом сборку. Корневой `npm run build` шлюз не вызывает.
31. **Сверка выборок.** `gates.json` сверяется с пересчетом 10 000 сидов BAL-005 (150 000 полей): все счетчики совпадают. Допуск долей ворот — 0,5 п. п. (BAL-010) на этой выборке; запас на текущих данных лучше 0,1 п. п.
32. **Тест ECO-007 и SEC-004.** 10 000 случайных последовательностей действий (`run.test.ts`), около 55 с при полной нагрузке; таймаут 120 с.
33. **Порядок записей побега.** `run.test.ts` фиксирует, сколько записей волн есть на каждом шаге (после боевой победы текущая волна есть без ворот). Сервер принимает побег по этому правилу (см. server/README, «Что проверяет submit»).

## Открытые пункты и следующие шаги

- Postgres-адаптер для репозиториев и леджера (следующая итерация). Сейчас все правила чистые функции.
- Telegram Login, друзья, рефералы (следующая итерация).
- Оплата Stars и выключатель продаж: в ядре их нет. Магазин на сервере должен отдавать `payments_enabled=false`.
- Значения со статусом `open` (`openBalanceEntries()`, 160 записей): тексты карт, состав волн, урон Рыцаря, Друида и лягушки. Пока они открыты, релиз не собирается (`release:check`).
- TV-002: поле с `attempt ≥ 1` (см. Допущение 27). Нужна поправка спецификации или владельцем правила GEN-014.
- Кросс-платформенные тесты (Python 3, Chromium, WebView Telegram, TV-003). Golden уже есть, сверки в других средах нет.
- CI-проверка `balance:check` (BAL-008): пересборка `gates.json` и побайтное сравнение. Сейчас сверка есть в тестах; CI-конфигурации в репозитории нет.
- `CORE-009` и `BAL-002` (сборка релиза): шлюз есть, автоматической сборки релиза в CI нет.
